1. アンソロピック Claude Ship — 承認ポリシーは `.claude/approvals.yml` に、まず観察モードで、そして「誰も見ないままマージされうる」という警告(事実、会社発表・公式文書・媒体)

アンソロピックの発表記事「Introducing Claude Ship」(11月23日、claude.com)と開発者文書(code.claude.com)を直接読みました。ニュースルーム(anthropic.com/news)にはこの記事がなく、製品サイト側に掲載されています。Claude Ship は GitHub のプルリクエスト(PR)一件をレビュー → 修正 → 承認判定まで引っ張っていくエージェントの束で、三つで構成されます(会社が書いた名前のまま)。

  • Code Review — すでに正式提供(GA)。PR を複数の観点で読んで発見事項を集め、反対検証を経て分類した上で PR にコメントとして付けます。リポジトリごとに Quick・Standard・Deep の三段階から一つを選びます。
  • PR Steward — ベータ。失敗した CI 検査、マージ競合、人やレビューツールが残したレビュー意見を受けて修正コミットを上げます。プッシュのたびに「何を変え、どう戻すか」をコメントに書き、開発者は `@claude` で指示したり `@claude stop` で引き下がらせたりできます。会社はこのエージェントが「承認・マージはしないよう設計された」と書いています。
  • Claude Approvals — ベータ。チームがリポジトリに書いた承認ポリシーファイルを適用します。文書に書かれたパスは `.claude/approvals.yml` で、デフォルトブランチにこのファイルが上がると有効になります。ポリシーにはパスごとに「人が何人承認する必要があるか」と「Claude が承認レビューを付けてよい場所」を書き、シグナルとして Code Review の発見事項やチームが自然言語で書いた分類器を掛けられます。発表記事はこれを「より賢い CODEOWNERS ファイル」と呼びました。会社の推奨順序は — まず観察モード(observe-only)で有効にして判定だけを見守り、信頼ができたら GitHub のブランチ保護ルールに「この検査の通過必須」として入れよ、というものです。

開発者側には Claude Code の `/ship` コマンドができました — 変更をプッシュし PR を開きレビューし、フィードバック・失敗検査を処理する一束。何がマージされるかはその開発者の権限とリポジトリのブランチルールが決めると書かれています。管理者側は組織設定の Claude Ship 画面(Owner 権限が必要)でリポジトリ一つずつ、エージェント一つずつ有効にせよと文書が書いており、順序も書かれています — Code Review → PR Steward(最初は「手動(@claude steward)」トリガーで、支出上限を定める前は PR Steward に上限がないため) → Claude Approvals(ポリシーファイルが有効にし、観察モードから、観察モードも課金)。発表記事の文章では「リポジトリ一つから始め、月の支出上限を定め、ポリシーは信頼ができるまで観察モードで」です。

提供範囲と課金(会社が書いたもの)。Claude Team・Enterprise プラン、GitHub リポジトリ(GitLab は文書に「別途 CI 連携」としてのみ登場)。データ無保持(ZDR)・HIPAA 構成・顧客管理暗号化キーを使う組織は使えません。費用はトークン使用量として組織の利用クレジットから引かれ、プラン込み分とは別です。Claude Approvals は基本料金がありませんが分類器の実行はトークンで課金され、ポリシーが Claude のレビューを要求すれば観察モードでも Code Review が回って課金されます。無効化の順序も文書にあります — Approvals → PR Steward → Code Review の順で、ポリシーがレビューを呼んで課金しうるためです。利用クレジットを切っても有効のままのエージェントは回り続けて課金されるので「料金を止めるにはエージェントを切れ」と書いています。

警告も文書にあります。GitHub の自動マージ(auto-merge)やマージキューを「人の承認を要求しないポリシー」と一緒に使うと、誰も手を触れないまま変更がマージされうるという文章と、発表記事の画像説明の「Claude Ship は AI を使うためバグ・セキュリティ脆弱性・その他の問題を見逃しうる」という文章です。ポリシーが曖昧なときや変更がポリシー外のときにどうなるかは、二つのページには書かれていません(下位文書は未閲覧 — 下の「確認できなかったこと」)。

会社が発表した数値は自社事例だけです — 「Claude Code チームでは Claude が我々のコードの大部分を書く」、同チームのマージ PR が6月から9月の間に「2倍以上」、差し戻された PR の比率は「40%以上減少」。顧客企業の引用二つ(TELUS・カーバナ)は会社が選んだ推薦文です。TechCrunch(サラ・ペレス、11月23日)は発表記事と文書をリンクして同じ内容を伝え、新しい数値はありません。

比較基準として GitHub 文書「About code owners」を開きました。CODEOWNERS はリポジトリの `.github/`・ルート・`docs/` のいずれかに置くファイルで、ファイルパスのパターン → 担当者(@user・@org/team)を一行ずつ書くのがすべてです。PR がそのパスに触れると担当者に自動でレビューが要請され、ブランチ保護の「Require review from Code Owners」を有効にすれば担当者のうち一人の承認で要件が満たされます。パス以外の条件(変更内容・規模・時刻)は文法にありません。つまりこれまでリポジトリに書けた「承認ルール」は「どのパスは誰が」までだったのです。

2. グーグル検索 AI Mode の Personal Intelligence — 財布は「読み取りのみ」、ドライブ・Gemini アプリは数週間以内(事実、会社発表・媒体)

グーグル検索製品担当副社長ロビー・スタインの記事「A more tailored Google Search that's uniquely yours」(11月23日)を直接読みました。検索 AI Mode の Personal Intelligence(ユーザーが接続を許可したグーグルアプリの情報で答えを合わせる機能、NO.55)にはすでに Gmail・カレンダー・フォトが接続されており、今回Google Wallet が「今日から」、Google Drive と Gemini アプリが「数週間以内」に加わります。すべてオプトインで、「検索のパーソナライズ → 接続済みアプリ」でアプリごとにオン・オフでき、パーソナライズ全体も切れます。

財布接続の形が、この記事がこのニュースを選んだ理由です。記事は「財布を接続すると AI Mode はアカウント情報を読むことだけができ、お金を移したり管理したり投資したりすることはできない」と書きました。用途として挙げたのは支出の流れと「財務のマイルストーン」を見ること、日常の支出を減らせる所を探すこと、接続したカードの特典(キャッシュバックのカテゴリー・旅行特典・ポイント)を活かすことです。ドライブ接続は文書・シート・PDF を読んで「税務申告の準備計画」のような答えを作る例で、Gemini アプリとは文脈を互いに引き継げるようになります。「近く」答えの下の「Personalization」アイコンでどの文脈が使われたかを見られ、間違った文脈は言葉で直します(「もう菜食はしていない」)。記事にないもの — 国・プランの条件、数値、そしてショッピング・購入・決済への言及は一つもありません(「ショッピング」はサイトのメニューにあるだけ)。パス・会員証が含まれるかも書かれていません。TechCrunch(アイシャ・マリク、11月23日)は公式記事をリンクして「読み取り専用」を同じ意味で伝えました。9to5Google の11月13日の記事(Gemini アプリ側の Wallet 接続)は「米国限定」と書いていましたが、検索側の記事には地域がないため、この記事は地域を書きません。

NO.55でグーグル検索の Connected Apps(買い物 → 決済)とメタ Muse の「決済手段はエージェントに見えない」を書きました。今回の記事はその隣の欄 — 同じ会社の検索 AI が財布を「読み取り」でのみ開く選択です。「決済まで」と「読み取りのみ」が同じ会社の中で別の製品に別の形で付いています。

3. ハギングフェイス「ハーネスアダプター」— モデルはそのまま、ハーネスに合わせた LoRA を一つずつ、著者評価でトークン44〜60%減(事実、研究ブログ)

ハギングフェイスのブログ「Introducing harness adapters」(11月20日、ハギングフェイス所属の著者10名)を直接読みました。考えは単純です — エージェントの性能はモデルだけでなくモデルを包むハーネス(ツール呼び出し・コンテキスト管理・プロンプト — pi、OpenCode、Hermes Agent のようなコーディングエージェントの枠組み)によって変わるのだから、モデルの重みは固定しておき、ハーネスごとに小さなアダプター(LoRA)をハーネスの中で強化学習で訓練しよう、というものです。基盤モデルは Qwen3.8-27B 一つ、ハーネスは pi 1.5.2・OpenCode 2.2.7・Hermes Agent v0.22.6 の三つ、アダプターはハーネスごとに一つずつの三つと、その三つを合わせた「スーパーアダプター」一つです。訓練は検証器が採点するコーディング課題(公開データセット871個のうち「ときどき解ける」171個を選んで混ぜた1,050個)で GRPO 方式により、推論(thinking)モードは切って回しました。アダプター一つあたり B200 GPU 二枚だったと書かれています。

結果(すべて著者らの自己評価、pass@1 一回試行、thinking オフ)。pi ハーネスで Terminal-Bench 2.1 は40.0% → 56.5%(記事冒頭では 39% → 55%、課題あたりトークン 2.9K → 1.5K)、SWE-bench Pro の難問51問は40.0% → 64.0%(本文の別の箇所では 39.2% → 64.7% — 記事内で二つの数字が一致せず、著者は説明していません)。Hermes で Terminal-Bench 44.7% → 58.8%、OpenCode で 47.6% → 52.4%。三つを合わせたスーパーアダプターは六組平均で39.5% → 49.0%(新たに解けた71個、失った34個)、両方で解けた課題ではツール呼び出し53〜73%・トークン44〜60%減。著者ら自身が書いた限界 — ハーネスごとに基本設定が異なるためハーネス間のスコアは比較できない、スーパーアダプターの重みを Terminal-Bench で選んだのでそのスコアは「やや楽観的」である、thinking を入れた条件はほとんど試していない。学習になかった課題(AutomationBench 300個)では 23.0% → 27.0%(pi)程度で「ノイズの範囲内」と書いています(この部分は記事後半の要約で読みました)。ドル建ての費用削減は主張しておらず、トークン・ツール呼び出し数だけを数えました。アダプター・課題・軌跡はハギングフェイスに公開され、ライセンス表記は本文で見つけられず、第三者検証はありません。

同じブログの「How to build and maintain an agentic evaluation」(11月23日、アヴィジット・ゴーシュ・ベン・バーテンショー・アイリーン・ソライマン)はこの数字の読み方を与えてくれます — モデルを回す前に課題から検証(基準解答は通過し、「何もしないエージェント」と「近道」は落ちるか)、エージェントの「終えた」ではなく保存された成果物を採点、ハーネスのバージョン・コンテナ・モデル提供者を固定、pass@k と pass^k を並べる。記事が挙げた数字(著者引用) — ハーネスを変えると同じモデルの Terminal-Bench 精度が最大29.9ポイント動き、Terminal-Bench 2.1 は公開報告の後に89個中28個の課題を修正し、OpenAI の SWE-bench Verified 監査では調べた138問の59.4%に実質的な欠陥がありました。NO.52・56の「評価する側も評価される」の実務版です。

三つを合わせて読むと(解釈)

第一に、「承認」がリポジトリ内のファイルになり、そのファイルに初めてパス以外の条件が入りました。 GitHub 文書のとおり、これまでリポジトリに書けた承認ルールは「このパスはこの人」がすべてで、一人の承認で足りました。アンソロピック文書のポリシーファイルはそこに「何人」と「どんな条件ならエージェントが承認してよいか(自然言語分類器)」を加えました。これが良いか悪いかはこの記事は判断しません(利害関係の開示を参照)。私たちが読んだのは形です — NO.56で「ルールはエージェントが実際に読む場所になければならない」と書きましたが、今回の形はルールを人が読む文書ではなく、マージ経路が必ず通る検査(check)に移したものです。そしてその会社が同じ文書に「自動マージと一緒に使うと誰も見ないままマージされうる」と書いておいたことが、この形のもう一つの面です — 検査になった瞬間、人が抜けうるのです。

第二に、権限の形が「読み取り/書き込み」で分かれつつあり、同じ会社の中でも製品ごとに違います。 グーグル検索 AI の財布は「読み取りのみ」、同じグーグルの Connected Apps は「決済まで」(NO.55)、メタ Muse は「決済手段は見えず購入前に確認」(NO.53)。三つとも会社発表文の一文で、三つとも私たちが店やアプリでそのまま使える選択肢です。私たち側の教訓は「権限」を一塊で与えず、読み取りと書き込みを分けて書くこと — 財布のように「読み取りのみ」でも役に立つ接続はかなり多いのです(在庫照会、注文状況の確認、コメントの閲覧)。

第三に、変える場所はモデルではないかもしれません。 NO.48で「モデルを替えるのに数週間かかる」と「モデルの外に置いたものだけが引き継がれる」を書きました。ハギングフェイスの記事はその反対側です — モデルはそのままにして、モデルとツールの間に合わせた小さな部品でトークンを半分近く減らしたという著者評価です。数字は一モデル・三ハーネス・著者の自己評価で、学習外の課題ではノイズの範囲なので「アダプターが答え」とは書けません。書けるのは問いです — 私たちのエージェント費用の何パーセントがモデル単価で、何パーセントがハーネス(不要なツール呼び出し・長いコンテキスト)か。NO.46の課題あたり費用の表に「ツール呼び出し数」の列がなければ、今週その列から追加するのが、このニュースから無料で持ち帰れるものです。

私たちなら — コード・店・アプリを運営する小さなチームが今週やる三つ(実践)

  1. 承認ポリシーを、ツールと無関係に人の言葉で一枚先に書く。 当社のホームページリポジトリ(ニュースビルド・反映スクリプト)とアプリリポジトリそれぞれについて「誰が承認すればマージされるか」をパスごとに書き、パスの横に条件を付けます — 「翻訳ファイルだけが変わった PR は検査通過でよい」、「決済・会員・発送コードは人二人」、「スクリプト・設定は人一人 + 戻し方のコメント必須」。どのツールを使うにせよこの一枚が先で、GitHub の CODEOWNERS で書ける行(パス → 人)は今すぐ書きます。自動マージ・マージキューは「人の承認なしのポリシー」と一緒に有効にしないという行を一番上に置きます — この行は製品文書ではなく当社の運用ルールです。エージェントが承認判定をする日が来るとしても、NO.54の名簿に「承認エージェント」一行と月額上限・観察期間を先に書いた後です。
  2. エージェントに与える接続ごとに「読み取り/書き込み」を分けて書く。 NO.55の「ドアの表」(商品情報・カート・決済・会員情報)に列をもう一つ — 「読み取りのみ / 書き込みまで」。Hangul Cups(ハングルカップス)の注文状況・CourtMate の掲示板・Lia(リア)のコメントは「読み取りのみ」から始めてもエージェントのやることは多く、「書き込み」(発送・投稿・返金)は NO.56の上限欄と一緒に付けます。グーグルの記事の文章を私たちの言葉に置き換えると「この接続は読むことだけができ、移したり消したりはできない」 — この一行がストア説明・個人情報案内に入れられるかを広報と擦り合わせます。
  3. 課題あたり費用の表に「ツール呼び出し数」の列を入れ、評価課題三つを先に検証する。 NO.46・52の表(モデル/段階/完了/トークン/課題あたり費用/時間)にツール呼び出し数を追加し、同じモデル・同じ課題をハーネス(当社のプロンプト・ツール構成)二通りで回してトークンと呼び出し数の差を書きます — モデルを替えずに減らせる分がどれだけかを見るためです。その前にハギングフェイスの評価記事の三つの検証を当社の課題三つ(成分表の項目抽出・コマース問い合わせの分類・Lia(リア)の台本校正)に対して行います — 基準解答は通過するか、「何もしないエージェント」は落ちるか、近道は塞がれているか。一つでも通過すればその課題の過去のスコアは消して測り直します。Lia(リア)の台本には「承認ボタンをエージェントに渡す会社が最初に書いたのは『観察モード』だった」を学ぶトーンで、製品名と数値は reported としてのみ入れます。
