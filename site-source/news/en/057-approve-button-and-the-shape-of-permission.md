This week's three items reach the next square over — **where, and in what shape, permission is written.** Anthropic lets teams write "who has to approve" in a file inside the repository and wrote "just watch first"; Google opened the wallet to its search AI but set the shape to "read-only"; and Hugging Face released adapters fitted not to the model but to the space between the model and its tools (the harness). ## 1. Anthropic's Claude Ship — the approval policy goes in `.claude/approvals.yml`, observe mode first, and the warning that "changes can be merged without anyone looking" (facts; company announcement, official documentation, press)

We read Anthropic's announcement post "Introducing Claude Ship" (November 23, claude.com) and the developer documentation (code.claude.com) directly. The post is not in the newsroom (anthropic.com/news); it is up on the product site. Claude Ship is a bundle of agents that carries a single GitHub pull request (PR) all the way from **review → fix → approval judgment**, and it is made up of three parts (using the names exactly as the company wrote them).

- **Code Review** — already generally available (GA). It reads the PR from several perspectives, collects findings, puts them through counter-verification and classifies them, then posts them as comments on the PR. Each repository picks one of three levels: Quick, Standard or Deep.
- **PR Steward** — beta. It takes failed CI checks, merge conflicts, and review comments left by people or review tools, and pushes fix commits. Each time it pushes, it writes a comment on "what changed and how to revert it", and developers can direct it with `@claude` or make it step back with `@claude stop`. The company wrote that this agent is "designed not to approve or merge".
- **Claude Approvals** — beta. It applies the **approval policy file** the team has written into the repository. The path given in the documentation is `.claude/approvals.yml`, and it switches on once this file lands on the default branch. In the policy, per path, you write "how many people's approvals are needed" and "where Claude is allowed to post an approving review", and as signals you can attach Code Review's findings or classifiers the team **wrote in natural language**. The announcement post called this "a smarter CODEOWNERS file". The company's recommended order is — first switch it on in **observe-only mode** and just watch the judgments, and once trust has built, add it to GitHub's branch protection rules as "this check must pass".

On the developer side, a `/ship` command has been added to Claude Code — one bundle that pushes the changes, opens the PR, reviews it, and handles feedback and failing checks. It states that what gets merged is decided by that developer's permissions and the repository's branch rules. On the admin side, the documentation says to switch things on **one repository at a time, one agent at a time** from the Claude Ship screen in organization settings (Owner permission required), and the order is written out as well — Code Review → PR Steward (at first with the "manual (@claude steward)" trigger, **because PR Steward has no cap until a spending cap is set**) → Claude Approvals (switched on by the policy file, observe mode first, and **observe mode is billed too**). In the announcement post's words: "start with one repository, set a monthly spending cap, and keep policies in observe mode until trust builds".

Availability and billing (as the company wrote it). Claude Team and Enterprise plans, GitHub repositories (GitLab appears in the documentation only as "separate CI integration"). Organizations using zero data retention (ZDR), HIPAA configurations or customer-managed encryption keys cannot use it. Cost comes out of the organization's usage credits based on token consumption, separate from what the plan includes. Claude Approvals has no base charge, but classifier runs are billed in tokens, and if a policy requires Claude's review, Code Review runs and is billed even in observe mode. The order for switching off is in the documentation too — Approvals → PR Steward → Code Review, because a policy can call a review and incur charges. Even if usage credits are turned off, agents left on keep running and keep being billed, so it says "to stop the charges, turn off the agents".

The warnings are in the documentation as well. One sentence says that **if GitHub's auto-merge or merge queue is used together with "a policy that does not require human approval", changes can be merged without anyone touching them**, and the announcement post's image caption says "Claude Ship uses AI, so it may miss bugs, security vulnerabilities and other issues". What happens when a policy is ambiguous or a change falls outside the policy is not written on either page (sub-pages not opened — see "What we could not confirm" below).

The only figures the company announced are its own in-house case — "on the Claude Code team, Claude writes most of our code", merged PRs on that same team "more than doubled" between June and September, and the share of reverted PRs "fell by more than 40%". The two customer quotes (TELUS, Carvana) are testimonials the company selected. TechCrunch (Sarah Perez, November 23) linked the announcement post and the documentation and relayed the same content, with no new figures.

As a baseline for comparison, we opened the GitHub document "About code owners". CODEOWNERS is a file placed in one of the repository's `.github/`, root or `docs/` locations, and it consists entirely of one line per **file path pattern → owner (@user or @org/team)**. When a PR touches that path, a review is automatically requested from the owner, and if "Require review from Code Owners" is turned on in branch protection, approval from **one** of the owners satisfies the requirement. Conditions beyond the path (what changed, size, time) are not in the syntax. In other words, until now the "approval rules" you could write into a repository went only as far as "which path, by whom".

## 2. Personal Intelligence in Google Search's AI Mode — Wallet is "read-only", Drive and the Gemini app within weeks (facts; company announcement, press)

We read the post "A more tailored Google Search that's uniquely yours" (November 23) by Robby Stein, Google's vice president of product for Search, directly. Personal Intelligence in Search's AI Mode (the feature that tailors answers using information from the Google apps a user has allowed it to connect to; NO.55) already had Gmail, Calendar and Photos connected, and now **Google Wallet is added "starting today", with Google Drive and the Gemini app "in the coming weeks"**. All of it is opt-in, each app can be switched on and off under "Search personalization → Connected apps", and personalization as a whole can be turned off too.

The shape of the Wallet connection is why this article picked this item. The post wrote that **"when you connect Wallet, AI Mode can only read your account information; it cannot move, manage or invest money"**. The uses it listed are seeing spending patterns and "financial milestones", finding places to cut everyday spending, and keeping track of the benefits on connected cards (cashback categories, travel perks, points). The Drive connection is an example of reading documents, sheets and PDFs to produce answers like "a plan for preparing a tax filing", and with the Gemini app, context can be passed back and forth. "Soon", a "Personalization" icon beneath the answer will show which context was used, and wrong context is corrected in words ("I'm not vegetarian anymore"). What is not in the post — country and plan conditions, figures, and **not a single mention of shopping, purchasing or payment** ("Shopping" appears only in the site menu). Whether passes and membership cards are included is not stated either. TechCrunch (Aisha Malik, November 23) linked the official post and relayed "read-only" with the same meaning. A 9to5Google article from November 13 (on the Gemini app side's Wallet connection) wrote "US only", but the Search-side post gives no region, so this article does not state a region.

In NO.55 we wrote about Google Search's Connected Apps (grocery shopping → checkout) and Meta Muse's "payment method is not visible to the agent". This article is the square next to that — the same company's search AI choosing to open **the wallet as "read-only" only**. "All the way to payment" and "read-only" sit inside the same company, attached to different products in different shapes.

## 3. Hugging Face's "harness adapters" — the model untouched, one LoRA fitted to each harness, 44–60% fewer tokens by the authors' evaluation (facts; research blog)

We read the Hugging Face blog post "Introducing harness adapters" (November 20, ten authors affiliated with Hugging Face) directly. The idea is simple — an agent's performance depends not only on the model but on the **harness** that wraps it (tool calling, context management, prompts — coding-agent frameworks like pi, OpenCode and Hermes Agent), so keep the model weights frozen and **train a small adapter (LoRA) for each harness, with reinforcement learning inside that harness**. The base model is a single Qwen3.8-27B; the harnesses are three — pi 1.5.2, OpenCode 2.2.7 and Hermes Agent v0.22.6; the adapters are three, one per harness, plus one "super adapter" that merges the three. Training ran with GRPO on verifier-scored coding tasks (1,050 tasks, mixing in 171 "sometimes solved" tasks picked from 871 in public datasets), with reasoning (thinking) mode turned off. It says each adapter took two B200 GPUs.

Results (all the authors' own evaluation, pass@1 with a single attempt, thinking off). In the pi harness, Terminal-Bench 2.1 went **40.0% → 56.5%** (the opening of the post says 39% → 55%, with **tokens per task 2.9K → 1.5K**), and the 51 hard SWE-bench Pro problems went **40.0% → 64.0%** (elsewhere in the body it is 39.2% → 64.7% — the two numbers do not agree within the post, and the authors do not explain it). In Hermes, Terminal-Bench 44.7% → 58.8%; in OpenCode, 47.6% → 52.4%. The super adapter merging the three averaged **39.5% → 49.0%** across the six pairs (71 newly solved, 34 lost), and on tasks both solved, **tool calls fell 53–73% and tokens 44–60%**. Limitations the authors wrote down themselves — default settings differ per harness, so scores cannot be compared across harnesses; the super adapter's weights were chosen on Terminal-Bench, so that score is "slightly optimistic"; the thinking-on condition was barely tested. On tasks not seen in training (300 AutomationBench tasks) it was around 23.0% → 27.0% (pi), which they wrote is **"within noise"** (we read this part from the summary near the end of the post). They do not claim dollar savings; they counted only tokens and tool calls. The adapters, tasks and trajectories were released on Hugging Face, we could not find a license notice in the body, and there is no third-party verification.

The same blog's "How to build and maintain an agentic evaluation" (November 23, Avijit Ghosh, Ben Burtenshaw, Irene Solaiman) offers a way to read those numbers — **verify the tasks first**, before running a model (does the reference solution pass, and do a "do-nothing agent" and "shortcuts" fail?); **score the saved artifacts**, not the agent's "done"; **pin** harness versions, containers and model providers; put pass@k and pass^k side by side. The figures the post gives (as cited by the authors) — switching the harness moved the same model's Terminal-Bench accuracy by up to 29.9 points, Terminal-Bench 2.1 fixed 28 of 89 tasks after public reporting, and in OpenAI's audit of SWE-bench Verified, 59.4% of the 138 problems examined had substantive flaws. It is the practical edition of NO.52 and NO.56's "the evaluators get evaluated too".

## Reading the three together (interpretation)

First, **"approval" has become a file inside the repository, and for the first time that file contains conditions, not just paths.** Per the GitHub document, the approval rules you could write into a repository until now were entirely "this path, this person", and one approval was enough. The policy file in Anthropic's documentation adds "how many" and "under which conditions may the agent approve (natural-language classifier)". Whether that is good or bad is not something this article judges (see the disclosure of interests). What we read is the shape — in NO.56 we wrote that "rules have to sit where the agent actually reads them", and this shape **moves the rules out of a document people read and into a check that the merge path must pass through**. And the fact that the same company wrote in the same documentation that "used together with auto-merge, changes can be merged without anyone looking" is the other face of this shape — the moment it becomes a check, people can drop out.

Second, **the shape of permission is splitting into "read/write", and it differs product by product even within the same company.** Google Search AI's wallet is "read-only"; the same Google's Connected Apps go "all the way to payment" (NO.55); Meta Muse is "payment method not visible, confirmation before purchase" (NO.53). All three are single sentences from company announcements, and all three are options we can use as they are in our shops and apps. The lesson on our side is not to grant "permission" as one lump but to write read and write separately — there are quite a few connections that are useful even as "read-only", like the wallet (checking stock, checking order status, reading comments).

Third, **the place to change may not be the model.** In NO.48 we wrote "swapping a model takes weeks" and "only what you kept outside the model carries over". Hugging Face's post is the other side of that — leaving the model as it is and cutting tokens nearly in half with a small piece fitted between the model and its tools, by the authors' evaluation. The numbers are one model, three harnesses and the authors' own evaluation, and within noise on tasks outside training, so we cannot write "adapters are the answer". What we can write is a question — what percentage of our agent costs is the model's unit price, and what percentage is the harness (unnecessary tool calls, long context)? If NO.46's cost-per-task table has no "tool call count" column, adding that column this week is what can be taken from this item for free.

## What we would do — three things for a small team running code, a shop and an app to do this week (practice)

1. **Write the approval policy first, on one page in plain language, independent of any tool.** For our website repository (the news build and publish scripts) and our app repository, each, write "who has to approve before a merge" per path, but attach **conditions** next to each path — "a PR that changes only translation files just needs the checks to pass", "payment, membership and shipping code needs two people", "scripts and settings need one person plus a mandatory comment on how to revert". Whatever tool we use, this one page comes first, and the lines that can be written as GitHub CODEOWNERS (path → person) we write right now. At the very top goes the line that auto-merge and merge queues are not switched on together with "a policy without human approval" — that line is our operating rule, not a product's documentation. Even if the day comes when an agent makes approval judgments, it is only after a line for an "approvals agent", with a monthly cap and an observation period, has first been written into NO.54's roster.
2. **For every connection we give an agent, write "read/write" separately.** Add one more column to NO.55's "door table" (product information, cart, payment, member information) — "read-only / through to write". Hangul Cups order status, the CourtMate board and Lia's comments give an agent plenty to do even when started as "read-only", and "write" (shipping, posting, refunds) goes alongside NO.56's cap column. Put Google's sentence into our own words — "this connection can only read; it cannot move or delete" — and agree with PR on whether that one line can go into the store descriptions and the privacy notice.
3. **Add a "tool call count" column to the cost-per-task table, and verify the three evaluation tasks first.** Add tool call count to the table from NO.46 and NO.52 (model / level / completion / tokens / cost per task / time), and run the same model on the same tasks under two harnesses (our prompt and tool configuration) and record the difference in tokens and call counts — to see how much can be cut without changing the model. Before that, apply the three verifications from the Hugging Face evaluation post to our three tasks (ingredient-label field extraction, commerce inquiry classification, Lia script proofreading) — does the reference solution pass, does a "do-nothing agent" fail, are shortcuts blocked? If even one of them passes, that task's past scores are erased and measured again. For Lia's script, "the first thing the company handing the approve button to an agent wrote down was 'observe mode'", in a learning tone, with product names and figures only as reported.
